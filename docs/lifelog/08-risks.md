# 08. リスクと対処

「まず自分を疑え」の節。この構想が失敗するとしたら何が原因か、を先に書く。

---

## 1. 最大のリスク: 相手のいる会話を常時録音すること

### 法的な整理（日本）

- 会話の当事者の一方が録音すること（**一方当事者録音**）は、日本では原則として違法ではない。
  刑事上の問題は生じにくく、民事の証拠としても採用されうる。
- ただしこれは **「訴訟で不利益を被らない」という話** であって、
  **「相手に知られたときに関係が壊れない」ことは何も保証しない。**
- 業種によっては別の制約がかかる。守秘義務契約（NDA）を結んでいる商談、
  医療・法務・金融の相談、他社の入館ルールで録音禁止が明示されている場所などは
  **契約違反・規則違反になりうる**。ここは自分の顧客との契約を実際に確認すること。

> **この構想書は法的助言ではない。** 顧客との NDA に録音・記録に関する条項があるかは、
> 実際の契約書を読んで確認すること。必要なら弁護士に相談すること。

### 職業上の固有リスク

コンサルティング業務では、顧客の非公開情報を扱う。
その音声が自分のデバイスに 90日残り、要約が外部 LLM を経由するという構造は、
**顧客の情報セキュリティ規程に照らすと問題になりうる。**

### 設計に組み込む対処

| 対処 | 実装 |
|---|---|
| **ワンアクション停止** | ロック画面 Live Activity、コントロールセンター、Action Button、アプリ内長押し。どこからでも 1操作で止まる（[02](02-ios-recorder.md) §4） |
| **ジオフェンス除外** | 顧客オフィス、病院、その他登録した場所では自動停止 |
| **時間帯除外** | 就寝時間帯は録らない |
| **Focus モード連動** | 「睡眠」「プライベート」で自動停止 |
| **privacy: sensitive** | 該当エピソードは外部 LLM に渡さない。ローカル LLM のみ。エージェントの収集対象外 |
| **PII マスキング層** | 外部に出る前に人名・社名・連絡先を仮名化（[03](03-mac-pipeline.md) §3） |
| **ローカル完結の ASR** | クラウド ASR をデフォルトにしない |
| **音声 90日で自動削除** | 保持期間を無限にしない |
| **暗号化** | FileVault + 暗号化 APFS ボリューム。Tailscale 内のみに bind |

### 運用ルール（技術で解けない部分）

- **顧客との会議では、録音していることを伝える。** これが最も確実な防御であり、
  伝えられない場では録らない。
- 赤マイクインジケータが常時出るのは、隠せないという意味ではハンデだが、
  **「隠して録っているわけではない」という証拠**でもある。この見え方を利用する。
- NDA に記録の制約がある顧客はジオフェンス除外に登録する。
- 家族との会話をどう扱うかは、**家族に話して決める**。

## 2. 電池

| リスク | 実測で常時録音により **バッテリー寿命が 34〜50% 短縮**する報告がある |
|---|---|
| 影響 | 「肝心なときに電池切れで録れていない」が起きる |

対処:
- VAD で無音を捨てる（保存もエンコードもしない）
- 端末内 ASR は常時ではなくバッチ
- 低電力モードで自動的に機能を落とす
- 電池 20% で録音停止 + 通知
- **運用: MagSafe スタンド + 車載充電 + モバイルバッテリー。これが一番効く**

**受け入れる事実: iPhone 単独でノー充電の丸1日運用は成立しない。**
「日中どこかで 1 時間充電する」を前提に置く。それが許容できないなら、
Mac 会議録音のみに縮退するのが正しい判断。

## 3. 静かな故障

**最悪の失敗は「録れているつもりで録れていなかった」。**
1週間気づかずに過ごすと、その間の記録が丸ごと失われる。

| 検知項目 | 通知 |
|---|---|
| 直近 6 時間で 1 チャンクも取り込まれていない | macOS 通知 + iPhone プッシュ |
| マイク権限が落ちた | 即時 |
| セッション中断からの復帰が 3 回連続失敗 | 即時 |
| 未転送チャンクが 200 を超えた | 日次 |
| ストレージ残 1GB 未満（iPhone）/ 20GB 未満（Mac） | 即時 |
| パイプラインの dead ジョブ発生 | 日次 |

`90_Meta/health.md` に稼働状況を書き出し、デイリーノートからリンクする。

## 4. 「作ったが読み返さない」

**この構想が失敗する最も可能性の高いシナリオ。**

大量のログが貯まるが、実際には誰も読み返さず、
月数千円と保守の手間だけが残る。

対処:
- **Phase 0（1週間、Mac のみ）で判定する。** これが唯一の実効的な対策
- 「重要」タブと重要マークが使われるかを観察する。使われないなら、
  そもそも読み返す需要がない
- レポート末尾の「この推奨は使えたか（○/×）」欄で、エージェント成果物の当たり外れを記録する

**判定が No なら、Mac の会議録音だけで完結させる。** それは正しい撤退であって失敗ではない。

## 5. Vault の肥大化と Obsidian の劣化

年 3,000〜4,000 ノート増える。数年で数万ノートに達する。

対処（[04](04-obsidian-vault.md) §9 に詳述）:
- 全文と音声を Vault 外に置く（最重要）
- Bases を使う（Dataview を使わない）
- `importance <= 1` は 90日後に週次ロールアップして個別ノートを削除
- 年/月でフォルダ階層化

---

## 6. エージェントが「もっともらしいが中身のない」レポートを出す

マルチエージェント構成の典型的な失敗。

対処（[05](05-agents.md) §6 に詳述）:
- すべての事実主張に出典（Vault リンクか URL）を強制、ないものは `[要検証]`
- Step5 が引用元を実際に読んで照合する
- 「分からない」を明示的に許容する（埋め合わせの推測を禁じる）
- Step4 の「考えを変える条件」と Step5 の「最も強い反論」は省略不可

## 7. その他

| リスク | 対処 |
|---|---|
| 文字起こし精度が期待に届かない | Phase 0 でモデルを実測比較。日本語では kotoba-whisper が勝つ可能性がある |
| 話者分離が実用にならない | Mac 録音は 2トラック分離で回避。iPhone は「話者数だけ分かればよい」に期待値を下げる |
| Apple の API 変更 | `SpeechAnalyzer` は新しい API なので仕様変更の可能性。ASR は差し替え可能な構造にしておく |
| iOS のプロビジョニング切れ | Developer Program の開発用プロファイルは 1年。年 1 回の再ビルドをカレンダーに登録 |
| Claude API のコスト増 | 月次でトークン消費を可視化。閾値超過で enrich をローカル LLM に切替 |
| 引き継ぎ不能 | 本構想書と実装をリポジトリに残す。`transcript.json` は標準的な JSON にして、ツールが死んでもデータが読める形にする |

---

## 8. 撤退条件

以下のいずれかに該当したら、素直に縮退・撤退する。

1. Phase 0 の 1週間で、生成されたノートを一度も読み返さなかった → **Mac 会議録音のみに縮退**
2. 顧客との NDA に記録の制約があり、業務会話の大半が録音できない → **プライベート用途のみに縮退、または中止**
3. 電池運用が破綻し、日中に不便が勝った → **iPhone をやめて Mac のみ**
4. 家族・同僚から明確な拒否があった → **その場面では録らない。設計より人間関係が優先**
5. Phase 3 まで到達せず、エージェント活用の目処が立たない → **既製品（Plaud / Otter）に置き換えて自作をやめる**

**5 が重要。** 本構想の価値はエージェント活用にあり、そこに到達しないなら
既製品で十分だという結論になる（[07](07-market-research.md) §6）。
