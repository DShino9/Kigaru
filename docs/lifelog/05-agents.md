# 05. エージェント設計 — 5体分業の Obsidian 版

元ネタのスライド「5体のAIエージェントが分業する / 人間がやったのは『MTGの議事録を渡した』という1アクションだけ」を、
Notion → Obsidian、かつ **入力を「人が渡す議事録」から「勝手に貯まる会話ログ」に置き換えた**構成。

---

## 1. 全体フロー

```
        ┌──────────────┐
Step 1  │ vault-        │  Obsidian + 索引から関連ノートを収集
        │ collector     │  → _work/<run_id>/00_source.md
        └──────┬───────┘
               ↓
        ┌──────────────┐
Step 2  │ issue-        │  論点を構造化（イシューツリー・仮説）
        │ architect     │  → 30_Issues/<topic>.md
        └──────┬───────┘
               ↓
     ┌─────────┼─────────┐          ← 並列実行（3体同時）
     ↓         ↓         ↓
┌─────────┐┌─────────┐┌─────────┐
│research-││research-││research-│  Step 3
│market   ││analogy  ││customer │
└────┬────┘└────┬────┘└────┬────┘
     └─────────┼─────────┘
               ↓  → 40_Research/<run_id>_*.md
        ┌──────────────┐
Step 4  │ strategist    │  3本のリサーチ + 論点 → 戦略オプション3案 + 推奨
        └──────┬───────┘
               ↓
        ┌──────────────┐
Step 5  │ reviewer      │  事実確認・論理検査・反証 → 最終レポート
        └──────┬───────┘
               ↓
        50_Reports/2026-09-03_A社価格戦略.md
```

### スライドとの対応

| スライド | 本構想 |
|---|---|
| Step1 議事録取得（Notion から） | **Step1 会話ログ取得（Obsidian + FTS/ベクタ索引から）**。人が渡さなくても貯まっている |
| Step2 イシュー構造化 | 同じ。出力先が `30_Issues/` |
| Step3 並列リサーチ（市場・競合/アナロジー/顧客） | 同じ。ただし **customer は自分の過去会話ログも一次情報として使える**のが本構想の強み |
| Step4 ストラテジスト統合 | 同じ |
| Step5 レビュー&ブラッシュアップ | 同じ。加えて **引用元が Vault に実在するかの検証**を追加 |

## 2. 起動方法

### 手動（主）

```
/strategize A社の価格戦略
/strategize --tag 顧客/A社 --since 2026-08-01
/strategize [[2026-09-03_1405_A社定例]]
```

引数の解釈:
- ノートリンク → そのエピソードとその関連（同じ人・同じタグ・前後の会話）
- `--tag` → タグで絞り込み
- `--since` / `--until` → 期間指定
- 自由文 → ベクタ検索で関連エピソードを引く

### 半自動

- エピソードノートを `status: issued` にすると、夜間バッチが翌 02:00 に Step2 以降を実行
- 週次（日曜 03:00）に「今週の論点トップ3」について自動で Step1〜3 まで走らせ、
  Step4/5 は人が「これは深掘りする」と選んだものだけ実行（コスト制御）

## 3. 各エージェントの定義

`.claude/agents/` に配置する。以下は仕様であり、実装時にプロンプト本文を書き起こす。

### Step1: `vault-collector`

| 項目 | 内容 |
|---|---|
| 役割 | 与えられたテーマ・期間・タグに関連する会話ログを漏れなく集め、時系列に整理する |
| 使うツール | Read, Glob, Grep（Vault）/ Bash で `index.db` に FTS・ベクタ検索 |
| 入力 | テーマ文字列、期間、タグ、起点ノート |
| 出力 | `50_Reports/_work/<run_id>/00_source.md` |
| 出力の中身 | エピソード一覧（日付・タイトル・参加者・要約）、関連する決定事項・論点・ToDo の通し番号付きリスト、各項目に出典ノートのリンク |
| 制約 | `privacy: sensitive` / `excluded` のノートは**収集対象外**。除外した件数だけを報告する |
| 品質基準 | 「後段が出典を辿れること」。すべての記述に `[[ノート名]]` を付ける |

### Step2: `issue-architect`

| 項目 | 内容 |
|---|---|
| 役割 | 収集された会話から「本当に解くべき問い」を構造化する |
| 出力 | `30_Issues/<topic>.md` と `_work/<run_id>/01_issues.md` |
| 出力の中身 | ①イシュー（主問い）1つ ②サブイシュー（MECE に 3〜5個）③各サブイシューの現時点の仮説 ④仮説を検証/反証するために必要な情報 ⑤会話ログで既に分かっていること／分かっていないこと の切り分け |
| 品質基準 | サブイシューが MECE であること。「分かっていないこと」が具体的な問いの形になっていること（Step3 の検索クエリになる） |
| 注意 | 会話に出てきた論点をそのまま並べるのではなく、**構造化して階層にする**。ここが人間のコンサルワークで最も価値がある部分なので、上位モデルを割り当てる |

### Step3（並列3体）

3体は同時に起動する。それぞれ Step2 の「分かっていないこと」から自分の担当次元の問いを取り、Web と Vault を調べる。

#### `research-market` — 市場・競合・ベンチマーク

- 市場規模、成長率、主要プレイヤー、価格帯、直近の動き
- 競合の公開情報（IR、プレスリリース、料金ページ、求人）
- 出典 URL を必ず添える。**日付を明記**（情報の鮮度が判断を変えるため）
- 出力: `40_Research/<run_id>_market.md`

#### `research-analogy` — アナロジー事例

- 「他業界で同じ構造の問題をどう解いたか」を 3〜5 事例
- 事例ごとに「構造が同じ点」「違う点」「転用するなら何を変える必要があるか」を書く
- 単なる事例紹介にしない。**構造の写像を明示する**のがこのエージェントの価値
- 出力: `40_Research/<run_id>_analogy.md`

#### `research-customer` — 顧客・ユーザー

- **一次情報として自分の Vault（過去の会話ログ）を検索する。ここが本構想の最大の強み。**
  「顧客が実際に何と言ったか」を、記憶や議事録の要約ではなく発話そのものから引ける
- 加えて外部の調査（レビュー、SNS、業界調査）
- 出力: `40_Research/<run_id>_customer.md`。Vault 由来の引用は必ず `[[ノート]] 14:22` の形で出典を付ける

**3体共通の制約:**
- Web 検索に投げるクエリは **PII マスキング済みの語彙のみ**。実在の人名・非公開の社名を検索窓に入れない
- 分からなかったことは「分からなかった」と書く。埋め合わせの推測を事実として書かない
- 出典のない主張には `[要検証]` を付ける

### Step4: `strategist`

| 項目 | 内容 |
|---|---|
| 役割 | 論点 + 3本のリサーチを統合し、取りうる戦略オプションを提示する |
| 出力 | `_work/<run_id>/03_options.md` |
| 出力の中身 | ①状況の要約 ②戦略オプション 3案（それぞれ 打ち手 / 前提 / 必要な投資 / 期待効果 / リスク） ③評価軸（3〜4軸）での比較表 ④推奨案とその理由 ⑤推奨案が誤りになる条件（何が起きたら考えを変えるか） |
| 品質基準 | 3案が**本当に異なる戦略**であること（強度違いの3段階にしない）。⑤を必ず書くこと |

### Step5: `reviewer`

| 項目 | 内容 |
|---|---|
| 役割 | 検証して最終レポートに仕上げる |
| 出力 | `50_Reports/YYYY-MM-DD_<topic>.md` |
| 検証項目 | ①Vault 引用が実在するか（ノートと時刻を実際に読んで確認） ②Web 出典 URL が生きていて主張を支持しているか ③論理の飛躍（結論が前提から導けているか） ④リサーチ間の矛盾 ⑤反証（推奨案への最も強い反論を書く） |
| 出力の中身 | エグゼクティブサマリ / 論点 / 根拠（出典付き） / 戦略オプション比較 / 推奨 / 反論と応答 / 未検証事項リスト / 次アクション |
| 品質基準 | **検証で落とした主張を「落とした理由つきで」記録する**。黙って消さない |

## 4. 実装形態

### 案A: スラッシュコマンド + Task ツール（推奨・まずはこれ）

```
.claude/commands/strategize.md   ← オーケストレーション手順を書く
.claude/agents/vault-collector.md
.claude/agents/issue-architect.md
.claude/agents/research-market.md
.claude/agents/research-analogy.md
.claude/agents/research-customer.md
.claude/agents/strategist.md
.claude/agents/reviewer.md
```

- 実装が軽い。プロンプトの調整サイクルが速い
- Step3 の 3体は 1メッセージ内で同時に Task 起動すれば並列に走る

### 案B: Workflow スクリプト（安定運用に移行したら）

決定論的にステージを回し、各ステージの出力を JSON スキーマで縛る。
`pipeline()` + `parallel()` で Step3 を並列化し、Step2 の出力が出た次元から順に Step3 を流せる。
夜間バッチや週次自動実行に載せるならこちら。

**移行の判断基準**: 手動実行を 10 回ほど回してプロンプトが安定したら案B に移す。

## 5. コスト制御

| 施策 | 内容 |
|---|---|
| モデルの使い分け | Step1 は安いモデル（収集は機械作業）、Step2 と Step5 は上位モデル（構造化と検証が価値の中心）、Step3 は中位 |
| 入力量の制限 | Step1 の出力は 3万字を上限とし、超えたら重要度で足切り |
| Step3 の打ち切り | Web 検索は 1体あたり最大 10 クエリ |
| 週次自動は Step3 まで | Step4/5 は人が選んだものだけ |
| 実行ログ | `_work/<run_id>/run.json` に各ステップのトークン数と所要時間を記録し、`90_Meta/` で可視化 |

1回のフル実行で概ね ¥100〜500 の見込み。

## 6. 品質を担保する仕掛け

この種のマルチエージェント構成が失敗する典型は「もっともらしいが中身のないレポートが出る」こと。
対策を設計に組み込む:

1. **出典の強制**: すべての事実主張に `[[Vault ノート]]` か URL を付ける。ないものは `[要検証]`
2. **Step5 が実際に読みに行く**: 引用元ノートを Read して、書かれている内容と一致するか確認する
3. **「分からない」を許容する**: 各エージェントのプロンプトに「情報が足りなければ、埋めずに不足として報告せよ」と明記
4. **反証の義務化**: Step4 の⑤（考えを変える条件）と Step5 の⑤（最も強い反論）は省略不可
5. **人間の 1bit**: レポート末尾に「この推奨は使えたか（○/×）」を書く欄を置き、
   後で `50_Reports/` を振り返って**エージェントの当たり外れを自分で評価できる**ようにする

> 5 が一番大事。作りっぱなしにせず、当たったレポートと外れたレポートを見比べると、
> プロンプトのどこを直すべきかが分かる。
