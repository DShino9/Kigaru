## 2. 主要な設計判断とトレードオフ

各判断は「他の選択肢を検討したうえでこれを推す」形で記述する。実装時に覆してよいが、覆すなら理由を残すこと。

### 判断 1: 文字起こしをどこで行うか → **二段構え**

| 案 | 長所 | 短所 |
|---|---|---|
| A. iPhone 端末内のみ（iOS 26 SpeechAnalyzer） | 即時・無料・音声が端末外に出ない | 話者分離なし。長時間だと電池消費が増える |
| B. Mac のみ（mlx-whisper + pyannote） | 高精度・話者分離あり | 転送するまで結果が出ない。数時間の遅延 |
| **C. 両方（推奨）** | 即時性と精度を両立 | 実装が 2 系統になる |

**推奨: C**

- iPhone 側 = **速報テキスト**。録音直後から検索・想起に使える。精度は「思い出すための手がかり」で十分。
- Mac 側 = **正本**。話者名つきの高精度テキスト。レポート生成はこちらだけを使う。
- 正本が生成されたら速報を置き換える（`asr_stage: draft → final`）。

iOS 26 の `SpeechAnalyzer` / `SpeechTranscriber` は従来の `SFSpeechRecognizer` にあった約1分の制限とオンライン依存が撤廃され、日本語（ja_JP）を含む約40ロケールがオンデバイスで動く。この API の登場が本構想の実現性を大きく上げている。

### 判断 2: 音声の保持期間 → **90日ローリング + 重要マークは永久**

概算（Opus 24kbps mono）:

| 項目 | 値 |
|---|---|
| 1時間あたり | 約 10 MB |
| VAD 後の実効録音 | 6〜9 時間/日 |
| 1日 | 約 60〜90 MB |
| 1年 | 約 25〜33 GB |

音声そのものは意外に軽い。だが「聞き返すことはほぼない」ため、**90日で自動削除**。
`importance >= 4` または `pin: true` のエピソードは音声も永久保持。
文字起こしテキストは全期間永久保持（テキストは 1年で数百 MB 程度）。

### 判断 3: Obsidian に何を書くか → **構造化ノートのみ。全文は Vault 外**

全文をノートに入れると、1日 10 エピソード × 365日 = 年 3,650 ノート、各数万文字になる。
Obsidian の検索・グラフ・同期がいずれ破綻する。

- **Vault**: エピソードごとの構造化ノート（要約・論点・決定事項・ハイライト発話・メタデータ）。1ノート 1〜3 KB。
- **Vault 外 (`~/LifelogStore/`)**: 音声、全文 `transcript.json`、SQLite FTS5 索引、ベクタ索引。
- ノートの frontmatter に `transcript_path` を持たせて相互参照する。
- エージェントが全文を必要とするときは Vault ではなく **索引に問い合わせる**。

DB ビューは Dataview ではなく **Obsidian Bases** を使う。Bases は 5万ノート規模でもほぼ即座に描画でき、Dataview はモバイルで顕著に重くなる。

### 判断 4: iPhone → Mac の転送経路 → **選択制（既定は Tailscale 直送）**

| 案 | 長所 | 短所 |
|---|---|---|
| A. iCloud Drive の専用フォルダ | 実装が最も簡単。オフラインでも後から同期される | 音声が Apple のサーバを経由する |
| **B. Tailscale + HTTP POST（推奨・既定）** | 完全にローカル完結。Mac が寝ていても再送で追いつく | 実装がやや増える。Mac が長期オフラインだと端末に溜まる |
| C. ローカル Wi-Fi 直結（Bonjour） | 高速 | 外出先で送れず端末に溜まり続ける |

**推奨: B を既定にし、A をフォールバックとして設定で選べるようにする。**
「ローカル完結」を売りにする以上、既定でクラウドに音声を上げるのは方針と矛盾する。
ただし端末ストレージが逼迫したら A に自動フォールバックする逃げ道は用意する。

### 判断 5: iPhone と Mac の重複録音をどう扱うか → **両方取り込んで品質で正本を選ぶ**

在宅時は 2 デバイスが同じ会話を録る。単純に両方を文字起こしすると、同じ会議が 2 本ノートになる。

処理:

1. `segment` 段階で **時刻レンジが 60% 以上重なるエピソード**を検出
2. 各候補の品質スコアを計算 = `ASR 平均信頼度 × 0.6 + SNR 正規化値 × 0.4`
3. スコアの高い方を `device_primary` とし、低い方は `supplementary` として同一エピソードに統合
4. Mac 録音がある場合は原則 Mac が勝つ（システム出力トラックがあるため相手の声が明瞭）
5. iPhone 側にしかない区間（会議前後の廊下での会話など）は補完として結合

**Mac が録れているなら iPhone の同時録音は保険**、という位置づけで運用する。

### 判断 6: エージェントに生の会話を渡すか → **渡さない。マスキング層を必ず挟む**

Step3 の並列リサーチは Web 検索を伴う。ここに生の会話や実在の固有名詞が流れると、検索クエリという形で外部に漏れる。

```
[生の文字起こし]
   ↓ PII マスキング層（ローカル、決定論的）
   ├ 人名 → [PERSON_1] [PERSON_2] ...
   ├ 社名 → [COMPANY_A] ...（ただし公開情報の調査対象社名は許可リストで通す）
   ├ 電話/住所/メール/口座 → 削除
   └ privacy: sensitive のエピソードは丸ごと除外
   ↓
[エージェントに渡る要約・論点]
   ↓ 出力時にアンマスク（ローカルの対応表で復元）
[Obsidian のレポート]
```

マスキング表はローカルの SQLite に保持し、外部には決して出さない。

## 5. データフローの時間軸（典型的な1日）

| 時刻 | 出来事 |
|---|---|
| 09:00 | iPhone が出社中の独り言を録音。VAD が無音を捨てる |
| 10:00 | 在宅に切り替え。Mac が Zoom 起動を検知して自動録音開始 |
| 10:00-11:00 | iPhone・Mac 両方が録音。iPhone は端末内で速報テキストを生成 |
| 11:05 | Mac 録音終了。ingest が即座に処理開始（Mac 分は転送不要） |
| 11:20 | 正本の文字起こし + 話者分離完了。Obsidian にエピソードノートが出現 |
| 12:30 | iPhone を充電。溜まっていたチャンクが Tailscale 経由で Mac へ |
| 深夜 02:00 | 日次バッチ：デイリーノート生成、重要度スコアリング、90日超の音声削除 |
| 任意 | `/strategize` を叩くと 5 体のエージェントが走り、戦略レポートが生成される |
